# PostgreSQL Database Design

## 1. Purpose

This document defines the initial PostgreSQL persistence model for the
platform.

It translates the domain model, use cases, and REST API into durable
relational data.

This document defines:

- Tables
- Columns
- Relationships
- Primary keys
- Foreign keys
- Constraints
- Indexes
- State representation
- Transaction boundaries
- Concurrency requirements
- Audit/event storage
- PostgreSQL vs Redis responsibilities

This is a logical database design.

It is not yet the SQL migration implementation.

---

# 2. Database Responsibility

PostgreSQL is the authoritative source of durable business state.

PostgreSQL owns:

- Users
- Driver profiles
- Vehicles
- Rides
- Bids
- Assignments
- Ride lifecycle state
- Driver lifecycle state
- Durable ride events
- Durable timestamps
- Historical ride information

Redis is not an authoritative source for these entities.

---

# 3. General Conventions

## 3.1 Primary Keys

Use UUID identifiers generated by the backend/database.

Examples:

```text
user_id
driver_id
vehicle_id
ride_id
bid_id
```

Identifiers are opaque to clients.

Clients must not infer meaning from IDs.

---

## 3.2 Timestamps

All timestamps are stored as:

```text
TIMESTAMPTZ
```

and represented in UTC.

Typical fields:

```text
created_at
updated_at
started_at
completed_at
cancelled_at
```

The application may display timestamps in the user's local timezone.

---

## 3.3 Money

Monetary values must not use floating-point database types.

The initial design stores money as integer minor units.

Example:

```text
PKR 1,200.50

amount = 120050
currency = PKR
```

For currencies whose smallest unit differs, the currency determines the
interpretation.

A monetary value therefore consists of:

```text
amount
currency
```

---

## 3.4 Coordinates

Geographic coordinates are initially stored as:

```text
latitude  NUMERIC
longitude NUMERIC
```

The exact precision/scale will be finalized during migration design.

The design should leave room for introducing PostGIS if geographic queries
become sufficiently important.

# 4. Users

## users

Represents the application's internal identity.

```text
users
├── id
├── oidc_subject
├── email
├── display_name
├── status
├── created_at
└── updated_at
```

### Columns

| Column | Type | Constraints |
|---|---|---|
| `id` | UUID | PK |
| `oidc_subject` | TEXT | NOT NULL, UNIQUE |
| `email` | TEXT | nullable |
| `display_name` | TEXT | NOT NULL |
| `status` | user_status | NOT NULL |
| `created_at` | TIMESTAMPTZ | NOT NULL |
| `updated_at` | TIMESTAMPTZ | NOT NULL |

The OIDC subject is the stable external identity reference.

The backend must not use email as the primary identity key.

| Column | Type | Constraints |

# 8. Ride State

The initial ride states are:

```text
BIDDING
DRIVER_SELECTED
DRIVER_CONFIRMED
DRIVER_ARRIVED
TRIP_STARTED
TRIP_COMPLETED
CANCELLED
NO_DRIVER_FOUND
```

The database stores the current state.

The application/domain layer controls valid transitions.

The database should prevent obviously invalid nullability combinations where
practical, but complete state-transition rules belong to the domain layer.

Example:

```text
BIDDING
   ↓
DRIVER_SELECTED
   ↓
DRIVER_CONFIRMED
   ↓
DRIVER_ARRIVED
   ↓
TRIP_STARTED
   ↓
TRIP_COMPLETED
```

Failure paths:

```text
BIDDING
   ↓
NO_DRIVER_FOUND

Any cancellable state
   ↓
CANCELLED
```

# 10. One Active Bid Per Driver Per Ride

The business rule requires:

```text
one active bid
per driver
per ride
```

This should be enforced at the database level.

Use a partial unique index:

```sql
CREATE UNIQUE INDEX bids_one_active_per_driver_ride
ON bids (ride_id, driver_id)
WHERE status = 'ACTIVE';
```

This protects against concurrent requests.

The application should still validate the rule before attempting the insert/update.

The database is the final safety boundary.

---

# 11. Bid State

Initial states:

```text
ACTIVE
WITHDRAWN
SELECTED
EXPIRED
```

The application controls valid transitions.

Conceptually:

```text
ACTIVE
  ├── WITHDRAWN
  ├── SELECTED
  └── EXPIRED
```

A selected bid represents the bid chosen by the rider.

The winning assignment is additionally represented on the Ride.

This duplication is intentional:

```text
bids.status = SELECTED
rides.driver_id = selected driver
rides.agreed_fare_amount = selected amount
```

The Ride contains the authoritative current assignment.

The Bid preserves which offer was selected.

---

# 12. Bid History

The current `bids.amount` represents the driver's current offer.

Bid modifications should be auditable.

Rather than creating a new Bid row for every price change, the initial design
uses an event/history table.

## bid_events

```text
bid_events
├── id
├── bid_id
├── event_type
├── amount
├── created_at
```

Possible event types:

```text
SUBMITTED
UPDATED
WITHDRAWN
SELECTED
EXPIRED
```

### Columns

| Column | Type | Constraints |
|---|---|---|
| `id` | UUID | PK |
| `bid_id` | UUID | FK bids.id |
| `event_type` | bid_event_type | NOT NULL |
| `amount` | BIGINT | nullable |
| `created_at` | TIMESTAMPTZ | NOT NULL |

The event history is for audit/history.

It is not the primary source for current bid state.

### Columns

# 14. Driver Reservation

Driver selection is concurrency-sensitive.

The platform must prevent:

```text
Rider A → Driver X
Rider B → Driver X
```

from both succeeding.

The initial design uses the driver's durable assignment state through the
Ride relationship and transactional locking.

During bid selection:

```text
BEGIN;

SELECT driver
FROM driver_profiles
WHERE id = :driver_id
FOR UPDATE;

verify driver is not already committed;

lock/update the relevant ride;

assign driver;

COMMIT;
```

The exact SQL will be defined in the implementation/migration design.

The important requirement is:

```text
driver selection must be atomic.
```

Redis must not be the sole mechanism protecting this invariant.

---

# 15. Driver Availability

Driver availability is represented durably in:

```text
driver_profiles.availability_status
```

Initial states:

```text
OFFLINE
ONLINE
```

Additional operational states may be introduced later.

However, high-frequency ephemeral driver presence/location information should
not be written to PostgreSQL for every update.

PostgreSQL stores the business-level availability state.

Redis handles fast-changing operational state.

---

# 16. Driver Location

Driver GPS location is intentionally not stored as a row in PostgreSQL for
every update.

The initial architecture is:

```text
Flutter
   ↓
WebSocket
   ↓
Go
   ↓
Redis
```

Redis stores the latest operational location.

PostgreSQL may later store selected location history if a business requirement
exists.

This avoids turning PostgreSQL into a high-frequency telemetry database.

# 17. Relationships

The initial relationship model is:

```text
users
  │
  └── 1:1 ── driver_profiles
                 │
                 └── 1:N ── vehicles


users
  │
  └── 1:N ── rides
                 │
                 ├── N:1 ── driver_profiles
                 │
                 ├── N:1 ── vehicles
                 │
                 ├── 1:N ── bids
                 │              │
                 │              └── 1:N ── bid_events
                 │
                 └── 1:N ── ride_events
```

# 18. Foreign Key Rules

Foreign keys should use restrictive behavior by default.

Business records should not disappear because a related user or driver profile
was deleted.

The initial system should prefer deactivation/status changes over physical
deletion for business entities.

For example:

```text
Driver suspended
```

rather than deleting the driver.

Likewise:

```text
Vehicle inactive
```

rather than deleting historical vehicle information that is referenced by
completed rides.

---

# 19. Soft Deletion

The initial design does not require generic:

```text
deleted_at
```

columns on every table.

For business entities where historical integrity matters, use explicit status
fields.

Examples:

```text
users.status
driver_profiles.approval_status
vehicles.status
rides.status
bids.status
```

This avoids unnecessary complexity in every query.

Soft deletion can be introduced for specific resources when a concrete
requirement exists.

---

# 20. Important Indexes

Initial indexes should support actual access patterns.

### users

```text
UNIQUE (oidc_subject)
```

### driver_profiles

```text
UNIQUE (user_id)
INDEX (approval_status, availability_status)
```

### vehicles

```text
INDEX (driver_id)
INDEX (driver_id, status)
```

### rides

```text
INDEX (rider_id, created_at DESC)
INDEX (driver_id, created_at DESC)
INDEX (status, bidding_ends_at)
INDEX (status, created_at)
```

### bids

```text
INDEX (ride_id, status)
INDEX (driver_id, status)
UNIQUE (ride_id, driver_id) WHERE status = 'ACTIVE'
```

### bid_events

```text
INDEX (bid_id, created_at)
```

### ride_events

```text
INDEX (ride_id, created_at)
```

Indexes should be validated against real query plans after implementation.

We should not create indexes merely because a column exists.

---

# 21. Bidding Deadline

The authoritative bidding deadline is:

```text
rides.bidding_ends_at
```

The backend checks the deadline when processing:

- Bid submission
- Bid modification
- Bid withdrawal
- Bid selection

The client countdown is not authoritative.

A background process may mark bids as `EXPIRED`, but correctness must not
depend on a background process running exactly at the deadline.

For example:

```text
10:00:30
bidding deadline

10:00:31
driver submits bid

→ database/application rejects bid
```

even if an asynchronous expiration worker has not yet run.

---

# 22. Assignment Confirmation Deadline

The authoritative confirmation deadline is:

```text
rides.driver_confirmation_deadline
```

The backend validates this timestamp whenever the selected driver attempts
to confirm.

A background process may handle timeout/fallback processing.

Correctness must not depend solely on the background process.

# 23. Transaction Boundaries

Important business operations should execute within database transactions.

## Request Ride

```text
BEGIN

validate rider
calculate reference fare
create ride
create ride event

COMMIT
```

---

## Submit Bid

```text
BEGIN

validate ride
validate driver
validate vehicle
validate bidding deadline
create/update bid
create bid event

COMMIT
```

---

## Select Bid

This is one of the most important transactions.

```text
BEGIN

lock ride
lock/validate selected bid
lock driver
validate all eligibility rules
reserve driver
set ride driver
set ride vehicle
set agreed fare
set confirmation deadline
update bid status
create ride event
create bid event

COMMIT
```

Exactly one concurrent selection may succeed for a driver.

---

## Confirm Assignment

```text
BEGIN

lock ride
validate selected driver
validate confirmation deadline
validate ride state
set DRIVER_CONFIRMED
create ride event

COMMIT
```

---

## Start Trip

```text
BEGIN

lock ride
validate assigned driver
validate ride state
set TRIP_STARTED
create ride event

COMMIT
```

---

## Complete Trip

```text
BEGIN

lock ride
validate assigned driver
validate ride state
set TRIP_COMPLETED
create ride event

COMMIT
```

Payment settlement will introduce additional transaction/outbox requirements
later.

---

# 24. State Transition Enforcement

The application/domain layer is responsible for determining whether a state
transition is valid.

Example:

```text
BIDDING → DRIVER_SELECTED
```

is valid.

But:

```text
BIDDING → TRIP_COMPLETED
```

is invalid.

The database should provide additional constraints where useful, but we
should not encode the entire state machine into PostgreSQL CHECK constraints.

The state machine belongs in the domain/application layer.

---

# 25. Current State vs Event History

The system deliberately stores both:

```text
Current state
    +
Historical events
```

Example:

```text
rides.status
    = TRIP_STARTED
```

and:

```text
ride_events

RIDE_REQUESTED
BIDDING_STARTED
BID_SELECTED
DRIVER_CONFIRMED
DRIVER_ARRIVED
TRIP_STARTED
```

The current state provides efficient reads.

The events provide historical context and auditability.

Neither should be treated as a distributed event-sourcing system at this stage.

# 26. PostgreSQL vs Redis

| Data | PostgreSQL | Redis |
|---|---|---|
| User | Authoritative | No |
| Driver profile | Authoritative | Optional cache |
| Vehicle | Authoritative | Optional cache |
| Ride | Authoritative | Optional cache |
| Bid | Authoritative | Optional cache |
| Ride state | Authoritative | Cache only |
| Bid state | Authoritative | Cache only |
| Driver availability | Authoritative business state | Fast operational state |
| Live driver location | No | Yes |
| WebSocket connection state | No | Yes |
| Rate limiting | No | Yes |
| Short-lived coordination | No | Yes |
| Ride history | Yes | No |
| Bid history | Yes | No |
| Audit events | Yes | No |

Redis data may be lost and reconstructed where appropriate.

Loss of Redis must not destroy the authoritative business state.

---

# 27. Cache Invalidation Principle

Redis is an optimization.

Therefore:

```text
PostgreSQL
    ↓
authoritative state

Redis
    ↓
derived/ephemeral state
```

The system must remain logically correct if Redis is temporarily unavailable.

This does not mean every feature remains available during Redis failure.

For example, real-time location may temporarily degrade.

But completed rides, bids, assignments, and other durable business state must
remain intact.

---

# 28. Outbox Consideration

The platform will eventually need reliable integration between PostgreSQL
transactions and asynchronous events.

For example:

```text
PostgreSQL transaction
       ↓
Ride state changed
       ↓
WebSocket notification
```

We must avoid:

```text
DB commit succeeds
    +
WebSocket publish fails
```

causing an inconsistent external view.

The initial implementation should therefore consider a transactional
`outbox_events` table for reliable asynchronous publication.

This will be designed in detail before implementing production-grade
real-time messaging.

---

# 29. Auditability

Important business transitions should create durable events.

At minimum:

```text
Ride requested
Bid submitted
Bid updated
Bid withdrawn
Bid selected
Assignment confirmed
Assignment rejected
Driver arrived
Trip started
Trip completed
Ride cancelled
```

Events should include:

- Event ID
- Entity ID
- Event type
- Actor where applicable
- Timestamp
- Relevant metadata

Events are append-only.

Existing event records should not be modified as part of normal business
operations.

---

# 30. Data Retention

Initial retention policies:

- Completed rides: retained
- Ride events: retained
- Bid records: retained
- Bid events: retained
- User records: retained according to legal/business requirements
- Live location: ephemeral by default
- Redis operational state: ephemeral

Specific retention periods are deferred until legal, privacy, and operational
requirements are defined.

---

# 31. Migration Strategy

Database schema changes must be introduced through versioned migrations.

Example:

```text
migrations/
├── 000001_create_users.up.sql
├── 000001_create_users.down.sql
├── 000002_create_drivers.up.sql
├── 000002_create_drivers.down.sql
└── ...
```

Migrations must be:

- Versioned
- Repeatable in fresh environments
- Reproducible
- Reviewed before production deployment

Production migrations must account for:

- Existing data
- Lock duration
- Index creation cost
- Backward compatibility
- Rollback strategy

# 33. Design Principles

1. PostgreSQL is the source of truth for durable business state.
2. Redis is not a second database.
3. Business invariants should be enforced at the strongest practical layer.
4. Concurrency-sensitive operations require database transactions.
5. IDs are opaque UUIDs.
6. Money uses integer minor units.
7. Timestamps use UTC `TIMESTAMPTZ`.
8. Historical business records should normally be retained.
9. Status fields represent current state.
10. Event tables provide audit/history, not a full event-sourcing architecture.
11. Indexes must support real access patterns.
12. Database schema should support the domain, not dictate the domain.
13. High-frequency GPS telemetry should not be written to PostgreSQL by default.
14. Redis failure must not destroy durable business state.
15. Schema changes must use versioned migrations.
